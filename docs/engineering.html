Case study

Engineering

How the plugin is built, and the evidence behind it.

A generative MIDI effect that owns timing-safe generation across multiple algorithmic engines, wrapped for real hosts, with decisions and evidence kept on disk.

In short

Generative MIDI is a plugin that invents notes and rhythms for music software. This page shows how it is built: ten note-making engines, a control hub that connects them to the host app, and wrappers for the plugin formats. Everything below is backed by files in the public repository, and the page says plainly what is not done.

Problem

Problem / thesis

A good plugin story needs more than a nice-looking screen.

MIDI FX plugins fail employers’ diligence when the story stops at “clever UI.” The hard part is a coherent system: engines that generate musical events, a processor that bridges parameters safely, format wrappers that load in real DAWs, and records that show what was verified versus deferred.

Generative MIDI is that full stack for a macOS MIDI effect — development status v0.8.0 per STATUS.md — built so architecture and proof are drillable without a scavenger hunt.

Architecture

Architecture

Working inward from the music app: plugin format, control hub, note engines, then the screen. Layers from host boundary inward: format clients, PluginProcessor (APVTS + lifecycle), core engines and MIDI scheduling, then editor/UI.

  • Core engines — Euclidean, Algorithmic (Markov, L-System, Cellular, Probabilistic), Stochastic (Brownian, Perlin, Drunk Walk, Lorenz); Polyrhythm retained in core.
  • MIDI path — MIDIGenerator, clock/event scheduling, gate and ratchet controllers.
  • PluginProcessor — parameters (38 registered, 37 automatable), generator dispatch, host callbacks.
  • Formats — AU, VST3, Standalone verified locally historically; AUv3 configured in CMake with iOS docs (not store-ready). CI (.github/workflows/ci.yml) builds on macOS, iOS (AUv3), Windows, and Linux; pluginval runs on the VST3 build for macOS, Windows, and Linux.
  • Editor — LookAndFeel / steampunk craft; bitmap UI path documented; Polyrhythm (experimental) is selectable in the generator dropdown and APVTS; 11 factory presets; MIDI expression (AT/PB/CC note-on emit).

Hard parts

Where the work concentrates

  • Realtime / scheduling

    Music software has a hard deadline: if a plugin is a few milliseconds late, you hear a glitch. So the note-making code avoids anything that could cause a delay.

    Engineering detail

    Note generation must respect host block timing. Gate length and ratchet features are described in STATUS with sample-accurate intent. Steady-state hot path is allocation-hardened (Euclidean regen, ratchet offsets, algorithmic single-note, EventScheduler pre-reserved queue; over-capacity schedules dropped). Residual risk called out in STATUS: trained Markov map-key vector on lookup. Engine behavior is covered by Catch2 / ctest in CI (29 test cases, incl. headless host playhead smoke + polyrhythm layer persistence); host transport gating is also exercised via REAPER + TwelveTake MCP and the manual smoke checklist — not a published latency bench suite.

  • Parameter bridging

    A plugin’s settings must stay in sync between the screen, the music app’s automation, and saved projects. One shared list of settings keeps them aligned.

    Engineering detail

    APVTS choices drive engines and UI. The live generator choice list matches the editor: ten generators (Euclidean, experimental Polyrhythm, 4 algorithmic, 4 stochastic). Session migration bumps older 9-choice layouts to the current map.

  • Bypass / lifecycle

    A plugin has to start up, run, and switch off cleanly inside whatever app loads it. This is shown by build records and automated checks, not by claiming every music app was tested.

    Engineering detail

    JUCE plugin client lifecycle (prepare, process, editor attach) plus COPY_PLUGIN_AFTER_BUILD install paths. Host integration is evidenced by build artifacts, CI, and developer build docs, not by claiming every DAW certified.

  • Measurement contracts

    Claims are limited to what was built, tested, and checked. No invented coverage percentages.

    Engineering detail

    On-disk contracts are STATUS.md, BUILD_VERIFICATION.md, CHANGELOG, CI (.github/workflows/ci.yml + Catch2 / ctest ×29), QA findings, and the manual SMOKE_CHECKLIST — not invented coverage percentages. Prefer “build passed / tests ran / feature listed / smoke steps exercised” over marketing metrics.

Decisions

Selected design-decision highlights

  • Procedural LookAndFeel vs bitmap path The plugin’s look is drawn in code today. Image-based skins are specified, not finished. Victorian steampunk craft started as custom drawing; bitmap UI infrastructure and Synaptik asset specs document the next craft layer without claiming finished product polish.
  • SynaptikUIToolkit as git submodule A shared interface toolkit is pulled in as a separate repository pinned to a version, and the builds still pass after the move. Shared UI toolkit lives in art/ as a submodule; build verification records that formats still built after the migration.
  • Modulation system archived An unfinished feature was moved out of the way instead of shipped half-working. Incomplete modulation v1 moved under archive/ rather than left half-wired in the editor — honesty over feature theater.
  • Polyrhythm experimental in UI Polyrhythm (several rhythm layers playing together) is usable but marked experimental. Selectable at APVTS index 1 with a minimal layer editor. Remaining polish: step grid, layer session persistence — not a fake “deferred from UI” claim.

Roadmap

What’s next

What is left is depth, not basics. From STATUS — deferred depth, not missing basics:

  • MIDI expression depth — EXPRESSION UI + note-on AT/PB/CC emit shipped (static PB offset); continuous CC/PB modulation and MPE remain deferred.
  • Polyrhythm layer polish — step editing, polymeter visualization, layer XML persistence.

No App Store timeline is implied. See STATUS.md and ENHANCEMENTS.md for the longer backlog.
